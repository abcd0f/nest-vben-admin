# 组织、岗位与 RBAC 分阶段实施计划

## 1. 目标、范围与当前状态

目标是交付一个可管理、可验证的权限系统：用户隶属部门、可关联多个岗位和角色；角色拥有菜单/按钮/API 权限及部门数据范围；后端独立校验接口权限与数据范围；管理员能维护这些关系。

本计划使用以下九张表：`sys_dept`、现有 `sys_user`、`sys_post`、`sys_user_post`、`sys_role`、`sys_user_role`、`sys_role_dept`、`sys_menu`、`sys_role_menu`。其中 `sys_role_dept` **只表示角色的自定义部门数据范围**；菜单和按钮/API 权限由 `sys_menu` + `sys_role_menu` 表达。岗位是组织资料，不自动赋予角色或权限。

当前实施进度：A（约定与凭据）、B（组织基础）、C（角色关系）、D（权限资源）已完成。B 的迁移会将旧 `dept_id` 保留在 `legacy_dept_id`，新增 BIGINT 部门引用列；部署者需按 `docs/rbac-a-contract.md` 提供映射并运行 `script/backfill-user-depts.mjs`。旧 ID 不会被直接强转或清空。D 完成后继续按本计划进入 E。

### 完成定义

- 用户只能调用所持有效角色授予的接口；无权限返回 403，未登录返回 401。
- 对需要数据范围的操作，服务端只能读写角色允许的部门数据；直接改请求参数不能越权。
- 管理员能维护部门、岗位、用户、角色、菜单，以及各关联关系。
- 角色撤权、停用、用户停用后，下一次请求按最新权限判定；首期不缓存权限。
- 新密码不以明文存储；现有明文数据有明确处置方案；迁移不丢现有用户。

## 2. 先固定业务规则（阶段 0：不建表、不写业务代码）

以下决定应写入接口与数据字典，再开始迁移：

1. **部门树**：采用单父节点树；根部门的 `parent_id` 为空。部门是否允许停用、停用是否作用于子部门、部门删除采用“有引用则拒绝”还是软删除，先统一规则。本计划建议有用户或子部门时拒绝删除。
2. **用户归属**：一个用户有一个主部门，多个岗位通过 `sys_user_post` 关联；多个角色通过 `sys_user_role` 关联。现有 `dept_id` 要转换为与 `sys_dept` 一致的 ID 类型，并取消唯一约束。
3. **岗位含义**：岗位仅用于职位资料和筛选；不通过岗位继承角色。若以后需要“岗位自动授予角色”，另建明确的规则，不暗含在 `sys_user_post` 中。
4. **角色数据范围**：角色 `data_scope` 建议定义为 `ALL`、`DEPT_AND_CHILDREN`、`DEPT`、`CUSTOM`、`SELF`；仅 `CUSTOM` 使用 `sys_role_dept`。`SELF` 按业务记录的负责人/创建人判定，不能只靠 `dept_id`。
5. **权限码**：`sys_menu` 包含目录、菜单、按钮/操作类型。能保护 API 的操作项必须有稳定且唯一的 `permission_code`，例如 `system:user:list`。确定一个接口对应一个权限码还是允许多个码，并列出完整映射表。
6. **多角色合并**：对某个接口，先找出**授予该接口权限码的有效角色**，再合并这些角色的数据范围。不能把角色 A 的接口权限与角色 B 的宽数据范围拼在一起。范围合并采用并集；没有匹配角色时拒绝。
7. **登录与会话**：确定令牌有效期、退出后是否立即失效、是否需要续期和强制下线。若要立即撤销，需持久会话或令牌版本；这属于认证能力，可额外建会话表，但不混进九张业务表。
8. **管理边界**：确定谁能分配角色、配置角色范围、授予菜单；禁止一般管理员通过这些操作给自己扩权。至少保护初始管理员和最后一个具备授权能力的有效管理员。

**产出与验收**：部门树规则、数据范围判定表、接口权限码表、初始化管理员方案、已有 `dept_id` 数据映射方案。上述规则未定时不要执行相关建表迁移。

## 3. 表结构与建表时间总览

| 阶段 | 数据库动作 | 目的 |
| --- | --- | --- |
| 1 | 不建新表 | 先修密码写入与用户 ID 处理 |
| 2 | 新建 `sys_dept`、`sys_post`；迁移 `sys_user.dept_id` | 先建立组织基础，再给用户加外键 |
| 4 | 新建 `sys_user_post`、`sys_role`、`sys_user_role`、`sys_role_dept` | 建立用户、岗位、角色及自定义部门范围关系 |
| 6 | 新建 `sys_menu`、`sys_role_menu` | 建立角色可授予的资源与操作权限 |
| 8～11 | 不再为基础 RBAC 建表 | 实现登录、Guard、数据范围、管理接口和前端对接 |

所有表通过 `prisma/models/*.prisma` 定义，使用 Prisma migration 保存结构变更；`db push` 不作为正式环境部署手段。各阶段先在空库和有现存 `sys_user` 数据的测试库验证。

### 九张表的最小职责与约束

| 表 | 关键字段/关系 | 必须考虑的约束 |
| --- | --- | --- |
| `sys_dept` | `dept_id`、`parent_id`、名称、排序、状态、时间 | `parent_id` 自引用；防循环；部门业务编码若使用则唯一 |
| `sys_user` | 现有字段；`dept_id` 指向部门 | 去掉 `dept_id` 唯一约束；建立外键及普通索引；保留现有 `user_id` |
| `sys_post` | `post_id`、唯一 `post_code`、名称、排序、状态、时间 | 编码唯一；停用后不可新增分配 |
| `sys_user_post` | `user_id`、`post_id` | 联合主键/唯一、外键、按 `post_id` 反查索引 |
| `sys_role` | `role_id`、唯一 `role_code`、名称、`data_scope`、状态、系统角色标记、时间 | 编码稳定；系统角色修改/删除受限 |
| `sys_user_role` | `user_id`、`role_id` | 联合主键/唯一、外键、按 `role_id` 反查索引 |
| `sys_role_dept` | `role_id`、`dept_id` | 联合主键/唯一、外键；仅 `CUSTOM` 范围生效 |
| `sys_menu` | `menu_id`、`parent_id`、类型、名称、路由信息、`permission_code`、状态、排序 | 自引用、防循环；操作权限码唯一；目录/菜单展示字段按前端契约确定 |
| `sys_role_menu` | `role_id`、`menu_id` | 联合主键/唯一、外键；按钮/API 操作项用于后端授权 |

所有 ID 使用与现有 `user_id` 相容的 `BigInt` 方案，并在 HTTP 中按十进制字符串传输；不能再用 `+userId` 转成 JS `number`。关联表通过明确外键策略防止孤儿数据。是否软删除部门、岗位、角色、菜单应统一决定；若使用软删除，查询及授权必须过滤删除记录，唯一编码复用规则也需明确。

## 4. 详细执行阶段

### 阶段 1：修凭据与用户 ID（写代码；不建新表）

**前置**：阶段 0 的现有密码处理方案已确定。

**工作**：用户创建和密码修改改为强哈希；增加密码验证能力；对历史明文密码做强制重置或受控迁移。把“管理员重置密码”和“用户修改自己的密码”区分成不同操作。统一校验路径 ID 并转换为 `bigint`，对外 DTO 用字符串表示，避免现有控制器 `+userId` 的精度问题。

**代码位置**：`apps/gateway/src/modules/system/user`、`libs/auth`、相关 DTO、测试。

**验收**：新密码不以明文落库；历史账号能按迁移方案继续使用或收到重置要求；超出 `Number.MAX_SAFE_INTEGER` 的 ID 不会指向其他用户。

### 阶段 2：建立部门和岗位基础（第一次建表、改现有表）

**建表/迁移**：新增 `sys_dept`、`sys_post`。迁移 `sys_user.dept_id`：盘点现存值；建立对应部门；写入新部门 ID；取消旧唯一约束；增加普通索引和外键。已有值不能直接强制转换或丢弃。若旧值无法映射，应先产出异常清单并处理，再收紧约束。

**此阶段代码**：仅编写可重复执行的数据回填/校验脚本及迁移验证；业务 CRUD 留到阶段 3。保持旧用户接口可在迁移后正常读写。

**验收**：两个用户能指向同一部门；迁移前后用户数及关键字段一致；部门父节点引用有效；空库与有数据测试库均能部署。

### 阶段 3：部门、岗位基础管理（写业务代码；不建表）

**工作**：新增部门树查询、部门增改/启停/删除约束；新增岗位列表、增改/启停；用户创建/修改支持设置主部门，用户查询可按部门筛选。部门迁移、变更父节点时防循环；删除有子部门、用户引用的部门要按阶段 0 的规则处理。

**代码位置**：`apps/gateway/src/modules/system/dept`、`post`，扩展 `user` DTO/service/module，沿用项目现有分页、响应 DTO、异常处理风格。

**验收**：部门树正确；无法形成循环；同部门多用户正常；停用/删除与用户引用规则一致；原有用户接口仍通过回归测试。此时接口尚未完成 RBAC，不能将这些管理接口直接公开上线。

### 阶段 4：建立角色与关联表（第二次建表）

**建表/迁移**：新增 `sys_role`、`sys_user_post`、`sys_user_role`、`sys_role_dept`。建立唯一键、外键、反查索引；为角色加入 `data_scope` 和系统角色标记。若角色改为非 `CUSTOM`，历史 `sys_role_dept` 行是删除还是保留但忽略，应在服务端固定一种语义；本计划建议在事务中清空，减少误解。

**初始化**：创建系统管理员角色，并以受控脚本给现有管理员建立 `sys_user_role` 关系。脚本可重复运行，不写死生产密码或个人账号。

**验收**：用户可关联多个角色/岗位，角色可关联多个自定义部门；重复关系被唯一键拒绝；非法外键无法写入；现有用户保留。

### 阶段 5：角色、岗位分配与自定义范围管理（写业务代码）

**工作**：角色 CRUD、状态管理和数据范围配置；用户岗位批量替换、用户角色批量替换；角色自定义部门批量替换。批量操作在一个事务中验证所有目标存在且可用，再整体更新。禁止普通角色管理者分配高于自身管理边界的角色或部门范围；系统管理员的保护规则单独实现。

**代码位置**：新增 `system/role`，扩展 `system/user`、`system/post`；数据查询与事务仍走 `PrismaService`。

**验收**：可完成用户→岗位、用户→角色、角色→部门关联；无效或停用目标不会留下部分更新；不能删除最后一个有效授权管理员。管理接口在阶段 9 接入 Guard 前不得对外开放。

### 阶段 6：建立菜单/操作权限（第三次建表）

**建表/迁移**：新增 `sys_menu`、`sys_role_menu`。`sys_menu` 区分目录、页面菜单、操作项；目录/页面负责路由展示，操作项的 `permission_code` 对应后端接口或按钮权限。操作权限码非空且唯一；菜单没有权限码时不能被用于 API 授权。路由字段先与前端约定，避免为未使用的框架元数据建列。

**初始化**：登记现有用户、部门、岗位、角色、菜单管理接口的权限码；授予系统管理员角色相应操作项。初始化脚本可重复运行。新增接口必须同步登记权限码，不能仅在代码里写字符串。

**验收**：权限码唯一；角色与菜单的重复授权被唯一键拒绝；所有待保护接口都能找到对应启用的操作项；目录树和操作项关系正确。

### 阶段 7：菜单与角色授权管理（写业务代码）

**工作**：菜单树 CRUD、类型及父子关系校验、防循环；角色菜单批量授权与查询；按用户有效角色生成可见菜单和按钮权限。删除或停用菜单时，定义子节点及关联授权的处理规则；系统内置权限码更名须配合代码和数据迁移，不作为普通编辑字段随意修改。

**验收**：角色获授权后可得到对应菜单与操作码；失效角色/菜单不会出现在结果中；直接查询权限列表不会泄露其他角色的授权。

### 阶段 8：登录与身份认证（写代码；基础 RBAC 不再建表）

**工作**：在 `libs/auth` 实现登录、当前用户、退出及选定的续期方案；实现认证 Guard 并接入 `AppModule`。登录验证哈希；每次请求确认用户未停用、未软删除。请求身份只来自服务端验证的令牌，不能信任客户端提交的角色或部门。密钥和令牌时效放入配置并启动校验。

**可能的额外表**：若阶段 0 决定“退出/强制下线立即失效”，在本阶段前加独立会话表及迁移，或使用有明确持久化与失效策略的存储；它不替代九张业务表。

**验收**：未登录 401；无效/过期令牌 401；停用或软删除用户无法继续访问；退出语义与阶段 0 一致。

### 阶段 9：接口授权（写代码；保护所有管理接口）

**工作**：在 `libs/permission` 实现 `sys_user_role → sys_role_menu → sys_menu.permission_code` 查询，过滤停用/删除实体；新增权限装饰器、权限 Guard 和显式公开标记。每个管理接口声明操作码；没有声明权限的业务接口默认拒绝。已登录但无权限返回 403。

**关键边界**：菜单显示与按钮隐藏只是前端提示，真正的 API 判断必须发生在后端。角色菜单授权和用户角色变更后，下一次请求读取最新结果；首期不做权限缓存。

**验收**：匿名、无权限、有权限、多角色、撤权、角色停用、菜单停用全部覆盖；新增未声明权限的接口不会自动开放。

### 阶段 10：部门数据范围（写代码；使用 `sys_role_dept`）

**工作**：为明确需要隔离的资源逐个定义“数据所属部门”字段及查询规则；在服务层对列表、详情、更新、删除统一应用数据范围。`ALL`、`DEPT`、`DEPT_AND_CHILDREN`、`CUSTOM`、`SELF` 分别实现并测试；`CUSTOM` 从 `sys_role_dept` 取部门。多个角色只合并**授予本操作权限**的角色范围。创建数据时校验目标部门；修改部门时同时校验旧记录和目标部门，防止跨部门搬运。

**不要做的假设**：有 `sys_role_dept` 表不等于所有查询自动受限。每个业务资源都必须确认部门归属；无部门归属或用户无部门时，应有明确拒绝/特例规则。跨部门统计和导出也要经过相同范围校验。

**验收**：列表、详情、更新、删除、导出不能通过改 ID 或请求中的 `dept_id` 越权；“角色 A 有操作权限但范围小、角色 B 范围大但无此操作权限”的组合不能获得大范围数据。

### 阶段 11：前端对接、发布与回归

**工作**：与前端约定当前用户、菜单树、按钮权限、部门树、岗位和角色选择接口及 ID 字符串格式。前端按权限隐藏入口，后端继续独立授权。部署前在测试库演练三轮业务迁移、数据回填、管理员初始化和旧密码处置；检查日志脱敏、401/403 契约、角色保护和回滚方案。

**发布要求**：阶段 2～10 可以分支或 PR 分批开发，但管理接口不能在 Guard 生效前对外开放。首次生产发布需同时包含已演练的迁移、初始化数据、认证和授权保护，确认管理员可登录且普通用户无默认管理权限。

**最终验收矩阵**：匿名/普通/管理员；单角色/多角色；有效/停用/软删除用户；有效/停用角色与菜单；五种数据范围；角色撤权；部门迁移；岗位关联；最后管理员保护；迁移后原有用户数据保留。

## 5. 推荐的实施拆分

| 工作包 | 包含阶段 | 可交付结果 |
| --- | --- | --- |
| A：约定与凭据 | 0～1 | 规则确认、密码安全、ID 契约 |
| B：组织基础 | 2～3 | 部门/岗位表、用户部门迁移、管理接口 |
| C：角色关系 | 4～5 | 四张角色与关联表、分配接口、自定义范围配置 |
| D：权限资源 | 6～7 | 菜单及角色菜单表、权限码目录、授权接口 |
| E：鉴权与范围 | 8～10 | 登录、接口 Guard、部门数据范围 |
| F：交付 | 11 | 前端契约、迁移演练、端到端验收 |

每个工作包完成后运行对应测试并审查迁移；**工作包完成不等于可单独上线**。尤其在 E 完成之前，B～D 的新增管理接口不能暴露在生产环境。
